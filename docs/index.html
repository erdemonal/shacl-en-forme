Introduction

SHACL en Forme presents statistics on how the Shapes Constraint Language (SHACL) is used in public GitHub repositories. It is an independent research resource and is not endorsed by the W3C.

The analysis covers SHACL shapes, targets, property paths, Core constraint parameters, and SHACL-SPARQL. It provides occurrence counts and Git tree prevalence using data collected from verified GitHub repositories, excluding forks. The dataset reflects the state of the verified GitHub repositories as of 11 October 2026.

Definitions, syntax rules, and validation procedures are available in the SHACL 1.0 Recommendation.

1 Usage in Practice

1.1 Dataset and Coverage

How many repositories and distinct Git trees are included in the study?

A Git tree represents a snapshot of repository contents. Multiple GitHub repositories may reference the same tree. The analysis uses distinct Git trees to avoid counting identical repository snapshots more than once.

Repositories were verified based on SHACL shape declarations, Core target or constraint predicates, or structurally attached SHACL-SPARQL constraints in parsed RDF graphs. After excluding forks and Git trees without extracted SHACL shape documents, the final dataset contains 3,675 repositories representing 3,657 distinct Git trees.

Among 550,508 files identified for RDF processing, 548,135 were successfully parsed.

A file is counted as a SHACL shape document if it contains at least one SHACL shape. Files containing only annotations or validation reports are not counted.

Measurement Count
Analyzed Git trees 3,657
Shape documents 50,625
Parsed RDF files 548,135

The analysis compares class and property IRIs referenced by SHACL shapes with ontology declarations in the same Git tree. A match requires that the referenced IRI is declared in that tree as an ontology term explicitly typed as a class or property.

Result Git trees

At least one matching ontology term 2,304
No matching ontology terms detected 501

1.3.2 Referenced Vocabularies

Which vocabularies are referenced by SHACL shapes?

The analysis counts Git trees containing SHACL references to terms from public RDF vocabularies through constraints, targets, and property paths. Both simple and complex property paths are considered.

1.3.3 OWL and SHACL Constraints

How do SHACL constraints relate to ontology restrictions?

The analysis compares ontology restrictions with SHACL constraints on property cardinality and value types. Comparisons use shared property IRIs and, for cardinality and OWL value restrictions, matching class IRIs.

Property range comparisons covered 1,708 Git trees. In 90,296 distinct tree–property pairs, rdfs:range and sh:class or sh:datatype referenced identical IRIs.

OWL value restrictions were compared with sh:class and sh:datatype in 323 Git trees, using matching class IRIs. Identical value type IRIs were found in 40,758 owl:allValuesFrom comparisons and 6,852 owl:someValuesFrom comparisons.

Cardinality comparisons covered 401 Git trees, using OWL cardinality restrictions and sh:minCount or sh:maxCount. At the tree–property level, identical minimum bounds were found in 6,853 pairs and identical maximum bounds in 24,460 pairs.

1.4 Constraint Consistency

How common are conflicting SHACL constraints?

The analysis checks for conflicting combinations of SHACL Core constraints. For example, a DCAT profile requires a foaf:name value to be both an xsd:string literal and a blank node. These requirements cannot be satisfied simultaneously.

Constraints were checked separately for each RDF source document.

Measurement Count
Git trees with identified conflicts 86
Distinct document contents with conflicts 272
Total conflict detections 3,664

The findings are concentrated in a small number of Git trees. Four trees contribute approximately 75% of all detections, largely due to repeated or generated shapes. Some findings also come from test material.

1.5 Usage Contexts

The analysis describes SHACL shape documents through their file organization and references to application-domain vocabularies.

1.5.1 Document Characteristics

What do file organization and naming patterns reveal about SHACL shape documents?

File paths and names contain test or example references in 19,477 documents and generation-related terms in 338 documents. Ontology and application profile indicators were found in 1,431 documents. These categories may overlap.

Which application domains are represented in SHACL shape documents?

Application domains were identified using vocabulary references in SHACL constraints and property paths. The classification assigned 16,227 shape documents to at least one of the 12 application domains.

2.4 Shape Characteristics

How are SHACL shapes documented and configured?

The analysis counts these properties on shape subjects in the extracted Git trees, including resources that are not explicitly typed as sh:NodeShape or sh:PropertyShape.

Property Git trees Tree prevalence
sh:message 2,135 58.38%
sh:name 1,210 33.09%
sh:description 1,069 29.23%
sh:severity 1,048 28.66%
sh:order 436 11.92%
sh:deactivated 239 6.54%
sh:group 166 4.54%
sh:defaultValue 144 3.94%

sh:message is the most widespread of these properties. For severity, sh:Violation has the highest occurrence count, but sh:Warning appears in more Git trees. Severity values are counted only when declared, excluding the default sh:Violation.

Deactivation is less common. The value true appears in 216 Git trees, compared with 239 trees containing sh:deactivated declarations of any value.

Names and descriptions are more widespread than ordering, grouping, and default values.

4 SHACL-SPARQL

How is SHACL-SPARQL used in practice?

4.1 SPARQL-based Constraints

The analysis counts structurally identified sh:sparql links and explicitly typed SPARQL constraint nodes, counted per RDF file.

Measurement Count
Git trees 1,065
Tree prevalence 29.12%
sh:sparql links 85,496
SPARQL constraint nodes 25,073
Which SPARQL constructs are used in these constraints?

The analysis identified 84,467 links to parseable SELECT queries across 1,040 Git trees.

FILTER and NOT EXISTS are the most widespread constructs. Grouping and aggregation are considerably less common.

Although MINUS appears in the analyzed queries, its use is prohibited by SHACL 1.0.

4.2 SPARQL-based Constraint Components

How widely are custom SPARQL-based constraint components used?

Measurement Git trees Tree prevalence
Custom constraint components 102 2.79%
ASK-based validators 91 2.49%
SELECT-based validators 94 2.57%

SPARQL-based constraints appear in approximately ten times as many Git trees as custom constraint components. Much of the custom component usage comes from SHACL test suites and DASH, with additional components found in examples and other projects.
