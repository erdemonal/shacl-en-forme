Introduction

SHACL en Forme presents statistics on how the Shapes Constraint Language (SHACL) is used in public GitHub repositories. It is an independent research resource and is not endorsed by the W3C.

The analysis covers SHACL shapes, targets, property paths, Core constraint parameters, and SHACL-SPARQL. It provides occurrence counts and Git tree prevalence using data collected from verified GitHub repositories, excluding forks. The dataset reflects the state of the verified GitHub repositories as of 11 October 2026.

Definitions, syntax rules, and validation procedures are available in the SHACL 1.0 Recommendation.

1 Usage in Practice

1.1 Dataset and Coverage

How many repositories and distinct Git trees are included in the study?

A Git tree represents a snapshot of repository contents. Multiple GitHub repositories may reference the same tree. The analysis uses distinct Git trees to avoid counting identical repository snapshots more than once.

Repositories were verified based on SHACL shape declarations, Core target or constraint predicates, or structurally attached SHACL-SPARQL constraints in parsed RDF graphs. After excluding forks and Git trees without extracted SHACL shape documents, the final dataset contains 3,675 repositories representing 3,657 distinct Git trees.

Among 550,508 files identified for RDF processing, 548,135 were successfully parsed.

A file is counted as a SHACL shape document if it contains at least one SHACL shape. Files containing only annotations or validation reports are not counted.

Measurement Count
Analyzed Git trees 3,657
Shape documents 50,625
Parsed RDF files 548,135

1.2 Shape Distribution

How are SHACL shapes distributed across Git trees?

The dataset contains 3,159,949 distinct shapes. Some were explicitly typed as sh:NodeShape or sh:PropertyShape. Others were identified from SHACL targets, constraints, property paths, or references from other shapes. Each shape IRI was counted once per Git tree and each blank node once per file.

Share of trees Git trees Distinct shapes Share of distinct shapes
Top 1% 37 1,684,699 53.31%
Top 5% 183 2,570,629 81.35%
Top 10% 366 2,830,876 89.59%

More than half of these shapes occur in just 37 Git trees.

1.3 SHACL and Ontology Usage

A SHACL shape can refer to a class or property declared in the same RDF document or elsewhere.

1.3.1 SHACL References to Ontology Terms

How often are the terms used by SHACL shapes typed as classes or properties?

SHACL shapes used 384,106 distinct IRIs as classes or properties. An IRI counts as a match if an explicit rdf:type declaration identifies it as a class or property consistent with its use in SHACL. For example, if a shape uses ex:Student with sh:targetClass, a declaration of ex:Student as owl:Class or rdfs:Class counts as a match. If the same IRI is used as both a class and a property, a declaration matching either role is sufficient.

The analysis looked for these declarations in Git trees where each IRI was used. To find external declarations, it looked up term IRIs over HTTP and checked linked RDF documents and vocabulary files.

Declaration source Distinct IRIs Share of IRIs
Same Git tree only 184,491 48.03%
External RDF only 44,854 11.68%
Both 22,769 5.93%
Neither 131,992 34.36%

For 53.96% of the IRIs, a matching declaration was found in at least one Git tree where the IRI was used. External RDF provided matching declarations for a further 44,854 IRIs. In total, 252,114 IRIs had a matching declaration, or 65.64% of all IRIs considered.

1.3.2 Ontology Terms Shared Across Documents

How often does another RDF document declare at least one term used in a SHACL document?

Across the dataset, 44,748 SHACL documents used at least one IRI as a class or property. For each document, the search covered other files in the same Git tree and RDF documents retrieved from the web. A document appears in the Both row if at least one term had a matching declaration in another file in the same Git tree and at least one had a matching declaration on the web. These can be different terms.

Declaration source SHACL documents Share of documents
Same Git tree only 10,243 22.89%
External RDF only 11,072 24.74%
Both 9,913 22.15%
Neither 13,520 30.21%

In 31,228 of the 44,748 SHACL documents, at least one term had a matching declaration in another RDF document. Such matches occurred in 3,264 of the 3,636 verified repositories containing SHACL documents that used class or property IRIs.

For each of the 31,228 documents with a match, the analysis calculated the percentage of its distinct terms declared by the single RDF document with the most matches. The median was approximately 72%. A single RDF document declared all the terms in 8,571 SHACL documents. In 7,263 SHACL documents with two or more distinct terms, each matching RDF document declared only one of those terms.

1.3.3 OWL and SHACL Constraints

How often do SHACL constraints match the values derived from OWL restrictions and RDFS range declarations?

Section 1.3.2 identified SHACL documents that used terms declared in other RDF documents. The constraint comparison covered these document pairs and files containing both ontology statements and SHACL shapes. The comparison used the mappings in Astrea-KG to identify the corresponding SHACL constraint for each OWL restriction or RDFS range declaration.

For an OWL restriction on a class, the SHACL shape had to target that class and use the property from the restriction as its path. For an rdfs:range declaration, the comparison used the property path regardless of the target class. A match required the corresponding SHACL constraint to contain every value derived for that comparison. For exact cardinality, a derived value counted as present only if the same property shape specified it as both sh:minCount and sh:maxCount. 

# OWL restriction
ex:HenriFayolSeminar rdfs:subClassOf [
    a owl:Restriction ;
    owl:onProperty ex:startTime ;
    owl:cardinality "1"^^xsd:nonNegativeInteger
] .

# Matching SHACL constraint
ex:SeminarShape a sh:NodeShape ;
    sh:targetClass ex:HenriFayolSeminar ;
    sh:property [
        sh:path ex:startTime ;
        sh:minCount 1 ;
        sh:maxCount 1
    ] .

Each comparison pairs one constraint derived from an ontology with one SHACL document.

OWL restriction or RDFS range Corresponding SHACL constraint Comparisons Matches Match rate
owl:maxCardinality sh:maxCount 68,005 61,071 89.8%
owl:minCardinality sh:minCount 9,757 7,069 72.5%
owl:cardinality sh:minCount and sh:maxCount 18,208 11,884 65.3%
rdfs:range with a datatype sh:datatype 215,995 152,158 70.4%
rdfs:range with a class sh:class 195,963 125,926 64.3%
owl:allValuesFrom sh:class or sh:datatype 14,291 12,067 84.4%
owl:hasValue sh:hasValue 1,388 1,242 89.5%

The SHACL document contained all the derived values in 371,417 of the 523,607 comparisons, or 70.9%. In 46,692 comparisons, the corresponding SHACL constraint had at least one value, but at least one derived value was missing. In the remaining 105,498 comparisons, no value was found for the corresponding SHACL constraint in the required context.

1.4 SHACL Constraint Satisfiability

How many constraint structures are satisfiable?

A shape is satisfiable if there is an RDF graph in which at least one node satisfies all its constraints. 

ex:BuildingShape a sh:NodeShape ;
    sh:targetNode ex:EmseCoursFauriel ;
    sh:property [
        sh:path ex:address ;
        sh:minCount 2 ;
        sh:maxCount 1
    ] .

This shape requires at least two distinct addresses for ex:EmseCoursFauriel but allows at most one. No node can satisfy both constraints.

The satisfiability check used 12 SHACL Core parameters. These include all three value type parameters and both cardinality parameters in SHACL 1.0. The other seven are sh:and, sh:or, sh:not, sh:node, sh:property, sh:hasValue, and sh:in. Each sh:path had to be a single property IRI, as in sh:path ex:address.

A translation based on SHACL2FOL expressed the constraints of each shape and its referenced shapes in first-order logic. Let S(x) mean that node x satisfies the shape. The translation required at least one such node to exist.

∃x S(x)

Vampire checked the resulting theories for satisfiability. Across 394,133 distinct constraint structures, 386,150 were satisfiable and 970 were unsatisfiable.

Result Distinct structures Share of structures
All constraints can be satisfied together 386,150 97.97%
No node can satisfy all the constraints 970 0.25%
No conclusive answer 1,099 0.28%
Unsupported input 4,987 1.27%
Tool error 927 0.24%

2 Shapes and Constraints

How are SHACL shapes and their properties used in practice?

2.1 Shapes

The analysis identified 1,183,518 shapes explicitly typed as sh:NodeShape or sh:PropertyShape. Shape IRIs are deduplicated per Git tree, and blank nodes are counted per file. The 632 resources typed as both sh:NodeShape and sh:PropertyShape are counted only once in the total.

Implicit property shapes were identified in 3,225 Git trees. A separate analysis counted 1,008,575 such shapes, using distinct IRIs per Git tree and blank nodes per file. Most occur under sh:property, without a sh:PropertyShape type declaration. Likewise, these shapes are included in the Core constraint, property path, SHACL-SPARQL, and OWL–SHACL analyses.

Shape prevalence is calculated over 424,580 explicitly typed node shapes and 759,570 explicitly typed property shapes. Git tree counts may also include shape subjects that are not explicitly typed as sh:NodeShape or sh:PropertyShape.

4 SHACL-SPARQL

How is SHACL-SPARQL used in practice?

4.1 SPARQL-based Constraints

Which SPARQL constructs are used in these constraints?

The analysis counts sh:sparql triples and typed SPARQL constraint nodes per RDF file.

Measurement Count
Git trees 1,065
Tree prevalence 29.12%
sh:sparql triples 85,496
Typed SPARQL constraint nodes 25,073

The analysis identified 84,467 sh:sparql triples referencing SELECT queries that could be parsed, out of 85,496 triples, across 1,040 Git trees.

Although MINUS appears in the analyzed queries, its use is prohibited by SHACL 1.0.

4.2 SPARQL-based Constraint Components

How widely are custom SPARQL-based constraint components used?

Custom constraint components allow developers to define validation rules using SPARQL. Their use was analyzed by checking for mandatory custom parameter predicates in shapes from the same Git tree as the component definition.

Measurement Git trees Tree prevalence
Custom constraint components 102 2.79%
ASK-based validators 91 2.49%
SELECT-based validators 94 2.57%

The dataset contains 115 distinct SPARQL-based custom constraint component IRIs. This analysis covered 106 components. The other nine had no mandatory custom parameter predicates that could be used for this check. Parameter matches were found for 31 components, including 20 with matches in multiple shapes. No matches were found for the remaining 75.
